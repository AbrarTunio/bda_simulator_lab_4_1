Write the map, the reduce, and watch the shuffle in between.

In this lab you write a Java MapReduce job that adds up the bytes each host sent, run it on YARN over the two million events, then make it cheaper with a combiner, steer it with a partitioner, and break it on purpose with skew. The page explains the ideas in plain words first; the simulator then runs every command.

The shuffle in the middle is where the network cost is. Most of this lab is about making it smaller or more even.

Explained simply

Nine ideas, each used in a step of the lab.

1MapReduce in one picture

Think of counting votes in an election. Each polling station counts its own ballots (map). The tallies are sent to a central office sorted by candidate (shuffle). The office adds up each candidate's tallies (reduce).

Our job: each mapper reads lines and writes (host, bytes); the reducer adds up the bytes for each host.

2Map tasks and reduce tasks

Hadoop starts roughly one map task per HDFS block: events.json has 3 blocks, so 3 mappers. You do not choose that number. You do choose the number of reducers, and each reducer writes one output file.

That is why job output is always a folder of part files, never a single file.

3Key and value types (Writables)

Mapper<LongWritableText›TextLongWritable>

The first two types are what the mapper reads (the line's position in the file, and the line). The last two are what it writes (host, bytes). Hadoop uses its own compact types, like Text and LongWritable, because millions of them travel over the network.

4The shuffle is the expensive part

Between map and reduce, every (key, value) pair is sorted and sent to the reducer that owns that key. Here that is 2 million small records crossing the network. Everything you optimise in this lab is about this middle part.

The counter Reduce shuffle bytes measures it.

5The combiner: a mini-reduce before sending

Without
host042: 10, 20, 15, 30 … sent one by one
With combiner
host042: 75 sent once per mapper

Safe for sum, count, min and max. Not safe for an average: the average of averages is wrong. Send (sum, count) instead.

6The partitioner chooses the reducer

For each key it answers "which reducer gets this?". The default is a hash of the key, which spreads keys evenly but randomly. A custom partitioner can group related keys, for example host000 to host049 on reducer 0.

It chooses which reducer, never the order inside it. Inside a reducer, keys always arrive sorted.

7Counters: the job's dashboard

Every job prints counters: how many records were read, written, combined, shuffled and spilled. Reading them is the main skill of this lab.

CounterAnswers
Map input recordsDid I read everything?
Reduce shuffle bytesHow much went over the network?
Spilled RecordsDid memory run short?

8Skew: one reducer does all the work

If one key has most of the data, the reducer that owns it is slow, and the whole job waits for it. More machines do not help: one key always goes to one reducer.

Words you will meet

Input split
The piece of input one map task reads; about one HDFS block.
Mapper / Reducer
Your two Java classes: map() is called once per line, reduce() once per key.
Driver
The main class that configures the job and submits it to YARN.
Part file
part-r-00000: the output of reducer 0. One per reducer.
Spill
When a task's in-memory buffer fills up, it writes to local disk. Many spills mean memory pressure.
Job history
The record of finished jobs (counters, task timings), served by the JobHistoryServer on port 19888.

What this lab teaches

    

      

        
    
          
  1. Map, shuffle, reduce. Map tasks follow the input blocks (3 here); reduce tasks are your choice, and each writes one part file.
    2. 
          
  2. Counters tell you what really happened. The first run "succeeded" but wrote nothing; only the malformed_lines counter showed every line had been rejected. Never trust a job that finished; read its counters.
    3. 
          
  3. The shuffle is the cost. Without a combiner, 2,000,000 records (about 36 MB) crossed it. With one, 600 records (about 11 KB): a 99.97% reduction, with identical results.
    4. 
          
  4. A combiner must be safe. Sum, count, min and max are; an average is not, unless you carry (sum, count) pairs.
    5. 
          
  5. The partitioner decides placement, the sort decides order. Hash spreads keys randomly; a custom rule grouped 50 hosts per reducer. Each file is sorted, the set is not.
    6. 
          
  6. Skew defeats parallelism. One host with 60% of the events made one reducer handle seven times the records of the others. Adding reducers cannot split a single key.
    7. 
          
  7. History needs its server. Job history and the "History" link work only with the JobHistoryServer running.
    8. 
          
  8. It took about 90 lines of Java in three files to compute one grouped sum (about 105 with the partitioner; the sheet says roughly 120). Keep the number for lab 4.2, where Spark does the same in a few lines.
